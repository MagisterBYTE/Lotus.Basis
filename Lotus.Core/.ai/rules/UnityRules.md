# Правила качества кода Unity

Данный документ содержит правила и стандарты качества кода для Unity. Эти правила должны соблюдаться при написании, рефакторинге и проверке кода. Общие правила именования и качества — в `BaseRulesAndQuality.md`; здесь только специфика Unity.

## 1. Именование

### 1.1. Требования к наименованию файлов и Editor-типов
- **Правило**: Классы отдельных редакторов (`UnityEditor.Editor`) имеют суффикс `Editor`.
- **Правило**: Классы отдельных окон редактора имеют суффикс `Window`.
- **Правило**: Классы рисования атрибутов (`PropertyDrawer` / `DecoratorDrawer`) имеют суффикс `Drawer`.
- **Правило**: Суффикс `Editor` **не** использовать для runtime `MonoBehaviour` / обычных классов (избегать имён вроде `LotusCameraEditor` для игровой камеры).

### 1.2. Требования к наименованию аргументов
- **Правило**: В методах компонентов не использовать аргумент с именем `name` — путаница с именем компонента/`Object.name`. Унифицировать суффиксом: `elementName`, `windowName`.

### 1.3. Требования к наименованию типов
- **Правило**: Имена компонентов Unity (`MonoBehaviour`) начинаются с префикса `Lotus`.
- **Правило**: Имена пользовательских ресурсов (`ScriptableObject`) начинаются с префикса `Lotus`.

### 1.4. Требования к наименованию методов
- **Правило**: Методы-корутины, возвращающие `IEnumerator`, имеют окончание `Iteration` (`MoveToLinearIteration`).
- **Правило**: Методы только для режима редактора / design-time имеют окончание `InDesign` (`GetSpriteInDesign`).
- **Правило**: Суффиксы `InGame`, `InRuntime`, `InDesignEditor`, `InDesignRuntime` не использовать без явной необходимости в новом API (зарезервированы / устарели в пользу `InDesign` и обычных runtime-методов без суффикса).

## 2. Проектирование кода для Unity

### 2.1. Сериализация полей
- **Правило**: Сериализуемые данные компонента — `[SerializeField]` на non-public поле с префиксом `_`, плюс публичное свойство PascalCase при необходимости API.
- **Пример**:
  ```csharp
  [SerializeField]
  internal float _speed = 50f;

  public float Speed
  {
      get { return _speed; }
      set { _speed = value; }
  }
  ```
- **Правило**: Начальные значения полей задавать в области объявления (`Fields`). В `Reset()` можно повторно выставить значения по умолчанию для редактора.

### 2.2. Инициализация: два допустимых паттерна

**A. Компонент (`MonoBehaviour`) — инициализация в Unity lifecycle**
1. Простые значения — в объявлении полей; при необходимости — в `Reset()`.
2. Ссылочные/кэшируемые данные — в `Awake()` (псевдоконструктор) или в отдельном `OnInitXxx()` / `OnInit()`, который вызывается из `Reset()` и `Awake()`.
3. Если компонент создаётся динамически (`AddComponent` / `Instantiate`) и имеет инициализацию — обязательно реализовать `Awake()`.

**B. Статический диспетчер / сервис**
- Методы `OnInit` / `OnResetEditor` на static-классе (`XInputDispatcher.OnInit`) — первичная инициализация подсистемы, не путать с lifecycle компонента.

### 2.3. Назначение методов Unity lifecycle
1. `Awake()` — псевдоконструктор: безопасная первичная инициализация и кэш ссылок.
2. `OnEnable()` — включение: подписка на диспетчер подсистемы и доп. инициализация после включения.
3. `Start()` — только если нужен гарантированный порядок после чужих `Awake`.
4. `OnDisable()` — отписка от диспетчера подсистемы.
5. При удалении объекта информировать подписчиков **на следующем кадре** (отложенный вызов через корутину), чтобы не ломать текущий обход.
6. При `ExecuteInEditMode` метод `Start` вызывается в редакторе и после выхода из Play Mode — учитывать это в логике.

### 2.4. Регионы в Unity-компонентах
- Вместо `Constructors` использовать `#region Unity events` для `Reset` / `Awake` / `OnEnable` / `Start` / `OnDisable` / `Update` и т.п.
- Остальные регионы — по `BaseRulesAndQuality.md` §10.3 (`Fields`, `Properties`, `Main methods`, `Serialization methods`, …).

### 2.5. Сборка Editor vs Runtime
- Editor-код — в отдельной Editor-сборке (`*.Editor.asmdef`), runtime — без ссылок на `UnityEditor`.
- Не смешивать `UnityEditor.*` API в runtime-скриптах без `#if UNITY_EDITOR` только там, где dual-build осознан и минимален.

### 2.6. Границы NET library vs Unity
- Код под `#if UNITY_2017_1_OR_NEWER` / в Unity-сборках: если у Unity есть специализированный API — **использовать его** (`UnityEngine.Mathf`, `Time`, `Object.Instantiate`, `Debug.Log` через обёртки платформы и т.п.), а не дублировать через BCL без причины.
- Общий NET-код (`csproj` без Unity): BCL / платформенные типы Lotus; не тянуть `UnityEngine` / `UnityEditor` вне Unity-веток.
- LINQ, `Span<T>`, `async`/`await` — допустимы в NET library; в Unity runtime — только если совместимо с целевым игроком/IL2CPP и не ухудшает hot-path; в критичных местах циклов Unity предпочитать обычные `for`/`foreach` без LINQ.
- Для колбэков в UI/инспекторе Unity допустим `UnityEvent`; в обычном коде платформы — `Action`/`Func` по `BaseRulesAndQuality.md`.
